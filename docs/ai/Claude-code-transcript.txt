  How the code works: it handles each item in three phases:
  1. It changes the quality using the sell-by days before they count down.
  2. It lowers SellIn by one.
  3. If SellIn is now negative, it changes the quality a second time.

  So an item with SellIn = 0 already gets the expired rate on that day.

⏺ I wrote the testing strategy to docs/testing-strategy.md. Nothing is
  implemented yet, and I made no changes to code or tests.

  Three layers, each with a different job:
  1. Golden master: a large snapshot of the original code's output that catches
     any behaviour change. It has 8 names × 8 SellIn values × 8 Quality values
     (512 items), each run for 14 days. Each item gets one output line showing
     its day-by-day values, so a failing diff points straight at the case that
     changed. Writing our own plain text also avoids Verify leaving out zero
     values.
  2. Business-rule tests (R1–R9) in GildedRoseTest.cs: one test per requirement,
     each tied to the sentence in the spec it documents. For example,
     Quality_NeverIncreasesAbove50 has rows for both Brie and Backstage, because
     "never above 50" is one rule that applies to both.
     BackstagePass_QualityIncrease_DependsOnDaysUntilConcert has the rows 11→+1,
     10→+2, 6→+2, 5→+3, 1→+3, which reads like the tier table in the spec.
  3. Legacy-behaviour tests (L1–L5) in a separate class: behaviour the code has
     but the spec doesn't state, or contradicts. Each one is something the
     planned refactoring could easily change by accident:
     - L1: Brie gains +2 a day after its sell-by date.
     - L2: only the exact full names get special rules.
     - L3: Conjured items currently behave like normal items. The Conjured
       feature will edit this test on purpose.
     - L4: quality outside 0–50 is never corrected. This is the riskiest one,
       because AGENTS.md suggests "shared clamping in one place", and a
       Math.Clamp would silently change it.
     - L5: Sulfuras keeps whatever quality it's given, not just 80.

  Keeping L1–L5 apart means fixing a quirk later shows up as an explicit edit to
  that class, not as a quiet change to a requirement test.

  What the existing tests protect:
  - ThirtyDays: covers more than it looks. It hits every Backstage threshold,
    the truncation at 50, the 0 floor, the Brie cap and the +2 after the sell-by
    date. Its gap is out-of-range quality (L4), which is the riskiest case for
    this refactoring. It also misses near-miss names and Sulfuras with a quality
    other than 80. I'd keep it unchanged.
  - Foo: never had an approved baseline, so I'd delete it and let the golden
    master replace it.
  - GildedRoseTest.foo: is replaced by R1–R9, as you agreed.

  Left out on purpose:
  - No named tests for pathological inputs (Q11–Q14, e.g. null names). Your shop
    doesn't have these cases.
  - No named tests for Q4, Q7, Q8 or Q10, because they're already covered by
    rows in other tests or by the golden master. Section 5 of the doc gives the
    reason for each.

  Mutation testing: I chose the boundary rows so that the usual small code
  changes Stryker makes (for example < → <= on 11, 6, 0 and 50) are caught by a
  named test, not just by the golden master. That makes any survivors easier to
  interpret later. The table is in section 6.
